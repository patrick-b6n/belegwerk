# i18n & Formatierung

Die UI ist ausschließlich deutsch, trotzdem laufen **alle** UI-Texte über
[Paraglide JS](https://paraglidejs.com). Zahlen, Beträge und Datumsangaben
werden über `Intl` mit `de-DE` formatiert.

## Konvention: keine hartcodierten UI-Strings

- Jeder für Nutzer sichtbare oder vorgelesene Text steht in
  [`messages/de.json`](../messages/de.json) – auch `aria-label`, `title`,
  `placeholder`, `sr-only`-Texte, Toasts, Fehlermeldungen und der
  Dokumenttitel. Das gilt auch für die generierten shadcn/ui-Komponenten unter
  `src/ui/components/ui` (nach einem `shadcn add` englische Texte ersetzen).
- In Komponenten werden Texte nur über die generierten Message-Funktionen
  verwendet:

  ```tsx
  import { m } from "@/paraglide/messages.js";

  <Button>{m.home_toast_button()}</Button>;
  ```

- Keys sind `snake_case` und mit dem Bereich präfixiert, z. B.
  `bookings_title`, `bookings_form_amount_label`. Allgemein wiederverwendbare
  Texte bekommen das Präfix `common_` (z. B. `common_close`).
- Parameter statt String-Verkettung: `"bookings_count": "{count} Buchungen"` →
  `m.bookings_count({ count })`.
- Nicht übersetzt werden: CSS-Klassen, `data-*`-Attribute, Log-/Fehlertexte
  für Entwickler (z. B. `throw new Error(...)`) und Fachwerte aus der Datenbank.
- Business-Code gibt keine fertigen UI-Texte zurück, sondern Codes (z. B.
  `ParseAmountError`); die UI bildet sie auf Messages ab.

## Setup

| Datei                                  | Zweck                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------ |
| `messages/de.json`                     | Alle Texte (einzige Locale `de`)                                         |
| `project.inlang/settings.json`         | inlang-Projekt: Locales, Message-Format-Plugin                           |
| `project.inlang/paraglide.config.js`   | Compiler-Optionen, gemeinsam für Vite-Plugin und CLI                     |
| `src/paraglide/`                       | Generiert (git-ignoriert), nicht bearbeiten                              |
| `project.inlang/cache/`                | Build-Cache des Vite-Plugins (git-ignoriert, enthält absolute Pfade)     |

- `pnpm dev` / `pnpm build` kompilieren die Messages über das Vite-Plugin.
  Alle Compiler-Optionen (inkl. `outdir`) stehen nur in
  `project.inlang/paraglide.config.js`; `vite.config.ts` übergibt nur `project`.
- `pnpm typecheck` ruft vorher `pnpm i18n:compile` auf, damit `tsc` auch in
  einem frischen Checkout die generierten Typen findet.
- Das Message-Format-Plugin wird als devDependency aus `node_modules` geladen
  (nicht vom CDN), damit Builds offline und reproduzierbar laufen.
- Locale-Strategie ist nur `baseLocale`; es gibt keine URL-/Cookie-Erkennung.

## Format-Helper

Reine Funktionen in `src/business/format` (ohne React/Tauri), nutzbar von UI
und Business (z. B. später für den CSV-Export):

| Funktion                 | Beispiel                                                    |
| ------------------------ | ----------------------------------------------------------- |
| `formatCurrency(cents)`  | `123456` → `"1.234,56 €"` (geschütztes Leerzeichen U+00A0)  |
| `formatDate(isoDate)`    | `"2025-03-07"` → `"07.03.2025"`                               |
| `parseAmount(input)`     | `"1.234,56"` → `{ ok: true, cents: 123456 }`                |

Beträge sind immer Integer-Cent. `parseAmount` rechnet nur auf der
Ziffernfolge (keine Floats), rundet nie und liefert bei ungültiger Eingabe
einen Fehlercode: `empty`, `negative`, `tooManyDecimals`, `tooLarge`,
`invalid`. Leerraum ist nur am Rand und neben `€` erlaubt, nicht innerhalb
der Zahl (`"1 234,56"` ist ungültig). Der Punkt ist immer
Tausendertrenner: `"1.500"` ergibt 1.500 €. Eingabefelder sollten deshalb
eine Vorschau des erkannten Betrags zeigen.

`formatDate` nimmt bewusst nur ISO-Kalenderdaten (`YYYY-MM-DD`), kein `Date`:
so hängt das Ergebnis nicht von der Zeitzone des Rechners ab. Die Tests
laufen in einer Nicht-UTC-Zeitzone (`vitest.config.ts`), damit
Zeitzonenfehler auch auf UTC-Runnern auffallen.

Details und Grenzfälle stehen in den JSDoc-Kommentaren und Tests.
